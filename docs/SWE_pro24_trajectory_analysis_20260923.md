# MetaGPT Pro24 轨迹分析：此前修改是否起效

核查日期：2026-09-23。运行目录：`workspace/pro24_full_216_20260922`。逐题统计见 [JSON](SWE_pro24_trajectory_analysis_20260923.json)。

## 1. 结论与统计边界

**此前的适配确实在实际轨迹中发挥了作用，尤其是让 mini 完成实现、让 Reviewer 执行检查并反馈具体缺陷、让 Engineer 获得返修机会。** Ansible 和 OpenLibrary 都存在“审查发现真实缺陷 → 源码按反馈修改 → 正式评估通过”的明确例子。

但当前数据不能证明每项改动各自提升了多少通过率，也不能证明团队优于相同预算的单 mini。已完成 144/216 题，通过 69 题，完成部分通过率 **47.9%**；剩余 72 题因 API 额度阻塞。各域按队列执行，完成部分不是随机样本，不能当作最终 216 题成绩。此前两三题冒烟是定向难例，也不能直接作为全量实验的对照组。

| 域 | 已完成 / 计划 | 正式通过 | 已完成部分通过率 |
| --- | ---: | ---: | ---: |
| Ansible | 35 / 63 | 19 | 54.3% |
| Flipt | 35 / 54 | 11 | 31.4% |
| OpenLibrary | 42 / 60 | 26 | 61.9% |
| WebClients | 32 / 39 | 13 | 40.6% |

本轮实际配置是 Leader + 上游 mini-swe-agent Engineer + Reviewer，每题生成预算 25 分钟，各角色单次最大输出 16,384 tokens；调度为 `first_edit_fraction=0.6, repair_seconds=0`。**不是** Pro23 冒烟使用的 `0.4 / 120` 提前三次审查方案。运行中只修复过控制器将源码中的 `AuthenticationError` 误判为 API 鉴权失败的问题，没有更换 agent 算法或评估标准。

## 2. 哪些改动实际被使用

统计只读取每题合并的 `events.jsonl`，不重复累计 mini 原始事件。下表是机制被使用的证据，不是因果消融结果。

| 机制或现象 | 144 题中的观测 | 能支持的判断 |
| --- | ---: | --- |
| Leader 完成计划 | 135 题 | 大部分任务实际经过规划阶段；尚不能独立量化规划收益 |
| 审查交接包包含已观察到的文件路径 | 141 题 | 路径交接机制有实际数据，减少凭空猜目录的条件已具备 |
| Reviewer 执行读取/检查后，后续请求仍允许检查 | 134 题 | 此前“一次读文件后被迫给结论”的限制已被解除并实际使用 |
| `verification_followup` 补充验证 | 113 题 | inconclusive 后仍有继续验证的机会 |
| Engineer 有检查证据 | 132 题 | 大部分任务不止生成补丁，也进行了验证尝试 |
| 交接包中有当前工作树的通过证据 | 91 题 | 一部分验证能绑定到被审查的版本；通过局部检查不等于正式 resolved |
| 非空最终补丁 | 143 题 | 本轮主要瓶颈已不是空 patch；唯一空 patch 出现在额度耗尽的 Flipt case_035 |

69 个成功用例中，**17 个最终补丁与首次提交不同，52 个首末补丁相同**。全体 144 题分别为 40 和 104。若统计“任意中间提交曾变化”，则是 42 题、其中 18 题成功；两者不能混用，因为中途改动可能最终撤回。

“审查后发生工作树变化”也不能直接算作源码修复收益：创建、删除临时测试同样会触发事件。更不能把 17 个成功直接称为 Reviewer 挽救的 17 题，因为本轮没有独立评估首次提交。首末补丁相同也不意味着 Leader 无贡献，首次实现已经接收了其计划。

## 3. 两条明确的修复链路

### Ansible case_020：审查定位遗漏的权限分支

任务涉及 `atomic_move` 默认权限和文件创建提示。

1. 348 秒首次提交。Engineer 已实现主要需求，但“目标文件已存在”分支仍保留旧权限。
2. 491 秒 Reviewer 给出具体反馈：`test_atomic_move.py` 中三个用例失败，实际 chmod 使用 420（0644），要求 384（0600）；指出 `lib/ansible/module_utils/basic.py` 的对应分支。
3. 602 秒 Engineer 将该分支改为 `DEFAULT_PERM & ~umask`，并将 umask 获取移到共用位置。首次和最终 patch 的差异确认这是实际源码变化。
4. 后续聚焦仓库测试 43 项通过；正式评估 **FAIL_TO_PASS 3/3、PASS_TO_PASS 8/8，通过**。

这里的协作贡献很具体：Reviewer 用运行结果指出遗漏分支，Engineer 接到可执行反馈后完成修复。无需假设审查只是形式上的角色对话。

本题也暴露了额外成本：第二次提交已修复核心问题，但旧复现脚本失败记录仍阻碍批准，最终仍为 inconclusive。854.7 秒后的补充验证继续到 1034.1 秒，约多用 3 分钟，最终源码补丁与第二次提交相同。

### OpenLibrary case_018：审查发现方法放错类

任务要求在 `Author` 上实现 `merge_remote_ids` 等作者导入行为。

1. 900 秒首次提交，方法实际加在 `Edition` 类中。
2. 963 秒 Reviewer 指出具体类与行位置，并结合复现说明：作者对象调用该方法返回 infogami 的 `<Nothing>`，调用方解包失败。
3. 1012 秒 Engineer 将方法从 `Edition` 移到 `Author`，随后运行方法位置和作者导入行为检查，清理临时测试。
4. 1263 秒再次提交；正式评估 **FAIL_TO_PASS 23/23，通过**，本题没有 PASS_TO_PASS 条目。

这条轨迹说明“能读取实际源码、提供定位信息、留有返修时间”的协作链路已经工作。未正式评估首轮 patch，因此不把它写成已测得的“首轮失败 → 第二轮通过”对照实验。

证据入口：两题 `traces/*/events.jsonl` 的 `review_verdict`、`action`、`review_packet`；最终 `all_preds.jsonl`；正式报告位于 `logs/run_evaluation/pro24_full_216_20260922_297887bb_{ansible_020,openlibrary_018}/DeepSeek-V4-Flash-0731/<instance_id>/report.json`。

## 4. 时间预算已经足以支持真正实施，但早落代码仍重要

| 分组 | 题数 | 首次工作树改动中位数 | 生成流程耗时中位数 |
| --- | ---: | ---: | ---: |
| 全体已完成 | 144 | 4.30 分钟 | 20.19 分钟 |
| resolved | 69 | 3.54 分钟 | 18.65 分钟 |
| unresolved，不含空 patch | 74 | 5.06 分钟 | 21.78 分钟 |

首次改动早于 5 分钟的任务通过 46/83；5–10 分钟为 20/47；10–15 分钟为 3/12；超过 15 分钟为 0/1；另有一题没有改动。首次工作树改动可能包含临时测试，不等同于首个有效源码修复。

这些数据说明本轮不是几十秒草率提交：实际生成流程中位数约 20 分钟。但更难的题本来就会更晚修改，API 等待也会挤压时间，不能据此推断“强制提前编辑即可提升到 55%”。当前证据更支持改善实现与验证的时间分配，而不是继续普遍加长总预算。

## 5. 仍然存在的问题

### 5.1 审查结果与正式评估不一致

| 最后一次 Reviewer 状态 | 题数 | 正式通过 |
| --- | ---: | ---: |
| approved | 14 | 8 |
| inconclusive | 119 | 57 |
| changes_requested | 11 | 4 |

69 个正式成功中，只有 8 个最终被 Reviewer 批准。保留已有补丁并交给独立评估的机制因此很有价值；Reviewer 的批准率不能代替解决率。另一方面，14 个批准中仍有 6 个未 resolved，但其中 WebClients case_030 没有有效评估断言输出，不能把全部 6 个都当成已证实的行为误判。

明确的行为误判例子包括：OpenLibrary case_037，Reviewer 认定作者 key 构造符合要求，正式 `test_make_author_adds_the_correct_key` 仍失败；Flipt case_007、009、017 批准后正式 `TestLoad` 失败。它们说明少量自建复现通过不足以证明完整接口和配置兼容。

### 5.2 失败证据消解过于机械

`reviewer.py:publish_review` 用完整 command 字符串组织检查证据。加一个 `PYTHONPATH`、换脚本名或增删命令参数，就可能无法关联之前失败与之后通过。通过证据又必须属于当前工作树；旧检查、临时复现脚本自身错误因而容易长期残留。

源码允许 `expected_behavior / environment_blocked / unresolved` disposition，但批准门槛实际只豁免带证据的 `expected_behavior`；没有明确的“已由某次新检查验证修复”关联。不能简单忽略所有旧失败，合理的后续方向是给检查分配稳定标识，记录版本、替代关系和已修复证据。Ansible case_020 就是有具体证据的实例。

### 5.3 跨轮 mini 仍重建上下文

交接已包含计划、补丁、路径、检查与审查反馈，但每轮重新启动 mini，文件路径不等于已经理解的代码上下文。返修阶段仍有重读与重新制作复现的开销。应优先携带明确的未完成步骤和最小修正位置，而非继续增加泛化角色对话。

### 5.4 失败分类不能只看评估报告中的一个布尔字段

143 份非空补丁对应的正式报告中：69 resolved，66 有测试状态但未 resolved，8 没有可解析测试状态；另有一题空 patch 未进入实际评估。

这 8 份报告均标记 `patch_successfully_applied=false`，但运行日志均记录了 `Applied Patch`。本地 SWE-bench `grading.py:get_eval_report` 在找不到可解析测试结果时会提前返回该字段的默认值，**因此不能把这 8 题统计成 patch 应用失败**。

- Flipt case_001、006、012、026、034：输出有缺失符号、字段或签名不匹配等编译错误，通常需回到实现与公共接口契约定位。
- Flipt case_027：新增 CockroachDB 驱动导入后，缺少 `cockroach-go/crdb` 模块，属于依赖整合问题，不能笼统归为测试镜像不完备。
- WebClients case_024、030：输出只有测试起止标记，没有任何断言结果。当前封装只展开 Jest `assertionResults`，没有充分保留空结果时的退出码、stderr 和 suite 错误，现有日志无法确定是测试收集、编译还是其他初始化问题。这两题应保留失败结果，另行诊断评估链路，不能据此断言实现错误或通过。

本次仅分析与记录，没有修改失败分类代码、重跑付费实验或覆盖原结果。

## 6. 隔离与归因限制

已有 [隔离审计](../workspace/pro24_full_216_20260922/isolation_audit_20260922.json) 确认：144/144 生成容器断网并隔离 Git 历史，143/143 实际评估容器断网；69 个 resolved 均有非空成功 FAIL_TO_PASS，且没有 FAIL_TO_PASS/PASS_TO_PASS 失败。结果不是把 Reviewer 的自我评价当作正式通过。

另检查到 60 个镜像初始工作树带有差异，路径主要是锁文件、构建资源，以及两题依赖版本、两题 Selenium/PyYAML 集成测试兼容调整；一题有 auth.yaml，未在文档展示其内容。路径计数在 JSON，单题可能包含多个路径。收集补丁时会排除字节不变的初始差异，但这些文件仍是生成环境的一部分。抽查的 requirements 和集成测试变动符合环境适配用途，**这不等于已经完成所有文件的答案泄漏审计**。

当前最稳妥的归因是：此前修复降低了执行流程中断、空提交和无效角色交接的影响，mini 在实际预算内能完成多数任务的有效实现，部分任务确实受益于 Reviewer 定位缺陷。要量化团队的净收益，需要在相同任务、模型、预算与隔离条件下，对比单 mini 与团队，或独立评估首轮和最终补丁；不能仅凭这次阶段性通过率宣称协作算法带来全部提升。

后续优先级建议：先补齐空评估输出的诊断信息，再改进检查证据的修复关联与具体返修交接；保留当前实验结果，避免边跑边改后把不同实现混为同一基线。
